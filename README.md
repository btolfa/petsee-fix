# petsee — коррекция координат GPS-трекера apptrackpets

Реверс-инжиниринг протокола пет-трекера (`apptrackpets.com:5455`) и небольшой
сервис, который на лету исправляет «сбойные» координаты: трекер физически в
Хихоне (Испания, ~`43.53 N, 5.66 W`), а приложение показывает точку в
Атлантике (`-43.53, +5.66`) — инвертированы знаки широты и долготы.

## Что в потоке (реверс дампа `petsee.mitm`)

Дамп — reverse-proxy mitmproxy к `apptrackpets.com:5455`. Протокол — вариант
**GT06/Concox**. Кадр:

```
78 78 | FLAG(1) | PROTO(1) | ...payload... | 0D 0A
```

- `78 78` — магический заголовок, `0D 0A` — стоп (по нему делятся кадры).
- `FLAG` — байт флагов/подтипа. **Внимание:** это НЕ поле длины из
  классического GT06 (в длинных пакетах его значение не совпадает с длиной).
- `PROTO` — тип пакета.

Наблюдаемые типы (`python3 src/decode_dump.py petsee.mitm`):

| PROTO | Что это | Направление |
|-------|---------|-------------|
| `0x01` | login/приветствие | C→S, S→C |
| `0x08` | keep-alive | C→S |
| `0x13` | heartbeat (батарея/статус) | C↔S |
| `0x1a` | **WiFi/LBS-скан** (BSSID + RSSI + соты) для server-side геолокации | C→S, ack S→C |
| `0x10` | **GPS-фикс** (реальные координаты) | C→S |
| `0x97`, `0x44` | служебные ответы сервера | S→C |

Трекер бо́льшую часть времени шлёт `0x1a` (WiFi/соты — их геолокацию считает
сервер), а при захвате спутников присылает `0x10` с точными координатами.

### GPS-пакет `0x10`

```
78 78 15 10 | 1a 08 05 0c 1e 1f | 9a | 04 ab a4 87 | 00 9b 6c ac | 02 | 3c 2e | ff f3 00 | 0d 0a
        │  │   └ datetime(6)      │    └ lat(4)       └ lon(4)      │    └ status  └ хвост
      flag proto  YY MM DD hh mm ss  sat                          speed  course&status
```

- `datetime` = `2026-08-05 12:30:31` (год — от 2000) — совпадает с датой дампа.
- `lat/lon` = `|градусы| × 1 800 000`, big-endian, беззнаковые (только магнитуда):
  - `0x04ABA487 / 1800000 = 43.53202`
  - `0x009B6CAC / 1800000 = 5.65883` → это Хихон.
- `status` (`course & status`, 16 бит):
  - bit12 `0x1000` — есть фикс;
  - bit11 `0x0800` — долгота западная (lon отрицательна) *[стандарт GT06]*;
  - bit10 `0x0400` — широта северная (lat положительна) *[стандарт GT06]*;
  - bit0–9 — курс (здесь 46°).

## Диагноз бага

Статус в пакете = `0x3c2e`. **Стандартный** GT06-декод даёт
`+43.53202, -5.65883` (N, W) — правильный Хихон. Значит трекер отдаёт корректные
данные. Но приложение показывает `-43.53, +5.66` — т.е. оно интерпретирует
биты полушарий (bit10/bit11) **инверсно** стандарту и «отзеркаливает» точку в
Атлантику. Классический симптом «прыжка» при захвате GPS.

**Фикс:** инвертировать оба бита полушарий: `status ^ 0x0C00` (`0x3c2e → 0x302e`).
Меняются только 2 байта, курс (bit0–9) и магнитуда координат сохраняются, CRC в
этом протоколе нет — длина кадра не меняется. После этого баговое приложение
показывает правильный Хихон.

## Сервис

Две реализации, логика общая в [`src/gt06.py`](src/gt06.py).

### Вариант 1 — mitmproxy-аддон (как в исходном захвате)

```bash
mitmdump --mode reverse:tcp://apptrackpets.com:5455 -p 5455 \
         -s src/mitm_fix_addon.py
```

### Вариант 2 — автономный прокси (только stdlib, без mitmproxy)

```bash
python3 src/proxy.py --listen 0.0.0.0:5455 --upstream apptrackpets.com:5455
```

В обоих случаях трекер нужно направить на ваш хост:5455 (через DNS/hosts,
роутер или настройки самого трекера). Лог при срабатывании:

```
[coord-fix] 2026-08-05 12:30:31  приложение: -43.53202,+5.65883 -> +43.53202,-5.65883
```

### Вариант 3 — Docker / docker-compose

```bash
# автономный прокси (по умолчанию)
docker compose up -d --build          # слушает :5455, апстрим apptrackpets.com:5455
docker compose logs -f coord-fix

# апстрим/порт настраиваются через окружение
UPSTREAM=apptrackpets.com:5455 docker compose up -d --build

# альтернатива через mitmproxy (профиль mitm)
docker compose --profile mitm up -d mitm
```

Переопределить адреса без правки compose можно переменными `LISTEN` и
`UPSTREAM` (см. секцию `environment` в `docker-compose.yml`). Образ —
`python:3.12-slim`, без зависимостей, запуск от непривилегированного пользователя.

### Mirror в Traccar

Прокси вдобавок отправляет **Mirror** — сырые байты трекера, до
hemisphere-фикса — в Traccar (`MIRROR`, по умолчанию `traccar:5199`, порт
протокола Topin). Ответы Traccar выбрасываются, а его падение не влияет на
путь к Vendor Cloud. Подробности в [ADR 0001](docs/adr/0001-mirror-into-native-topin.md).

Traccar собирается из `traccar/Dockerfile`: это официальный образ той же
версии с `tracker-server.jar`, пересобранным с
[`traccar/topin-lte-cells.patch`](traccar/topin-lte-cells.patch) (соты в
LTE-раскладке 4+4 байта). Тест декодера Topin прогоняется прямо при сборке.

Нужен `.env` рядом с compose (он в `.gitignore`):

```
POSTGRES_PASSWORD=...
GEOLOCATION_KEY=...   # Google Geolocation API, для Network Scan
```

UI Traccar публикуется только на tailscale-адресе `100.64.0.18:8082`, а
публичный доступ идёт через Caddy (`traccar.zignet.win`).

```bash
python3 src/decode_dump.py petsee.mitm
```

## Оговорки

- Разбор потока — по стоп-байтам `0D 0A`; если бинарный payload когда-либо
  содержит `0D 0A`, кадрирование собьётся (в наблюдаемом трафике такого нет).
- Фикс применяется только к пакетам `0x10`. Координаты из WiFi/сот (`0x1a`)
  считает сервер — на них мы не влияем; но именно GPS-фикс вызывает «прыжок».
- Гипотеза об инверсии полушарий приложением проверена по одному GPS-пакету и
  согласуется с жалобой. Если после развёртывания приложение всё ещё врёт,
  трансформацию легко поменять в `fix_gps_frame` (`src/gt06.py`).
